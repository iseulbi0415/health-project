# 소화 안심 타이머 — 역류성 식도염 케어 & 러닝 관리 앱

역류성 식도염이 있는 사람이 **"이 끼니를 먹었으면 몇 시간을 기다려야 하는가"**를
판단할 수 있게 돕는 iOS 앱입니다.

임상 가이드라인은 "취침 2~3시간 전 식사를 피하라"는 **범위**만 제시하고, 샐러드를
먹었을 때와 삼겹살을 먹었을 때 어느 쪽을 적용해야 하는지는 알려주지 않습니다.
이 앱은 **그 판단을 끼니의 총 지방량으로 자동화**합니다.

### 웹에서 네이티브로

웹 클라이언트로 전체 사이클을 먼저 완주해 백엔드 REST API를 완성한 뒤, 이 서비스의
사용 맥락 — **식사 직후 즉시 기록하고 타이머를 확인하는** — 에는 네이티브 앱이 적합
하다고 판단해 iOS 앱으로 확장했습니다. 이후 기능 개발은 네이티브에 집중했으며,
**본 출품작은 iOS 앱입니다.**

백엔드는 처음부터 **특정 클라이언트에 종속되지 않는 REST API로 설계**했기 때문에,
클라이언트를 확장하면서도 서버는 수정 없이 그대로 사용했습니다. 백엔드 설정에 남아
있는 웹 관련 항목(CORS 허용 출처 등)은 이 과정의 흔적입니다.

## 주요 기능

### 1. 소화 안심 타이머 (핵심 기능)

끼니에 포함된 **모든 음식의 지방량을 합산**해 대기 시간을 차등 적용합니다.

| 끼니 총 지방량 | 타이머 | 근거 |
|---|---|---|
| 10g 미만 | 2시간 | ACG 가이드라인 권고 범위의 하한 |
| 10g 이상 ~ 25g 이하 | 3시간 | 권고 범위의 상한 |
| 25g 초과 | 4시간 | 고형식 90%가 위를 빠져나가는 데 걸리는 시간 |

**설계상 특징 세 가지**

- **끼니 단위 합산** — 개별 음식이 아니라 그 끼니 전체를 봅니다. 같은 음식도 수량이
  늘면 구간이 올라갑니다. (곱창 1개 → 2시간 / 2개 → 3시간)

- **안전 마진 규칙** — 타이머가 이미 동작 중일 때 새로 계산된 시간이 남은 시간보다
  짧으면 무시하고 긴 쪽을 유지합니다. **값이 짧아지는 방향의 갱신은 허용하지 않습니다.**
  가벼운 음식을 나중에 먹었다고 해서 앞서 먹은 기름진 음식이 소화된 것은 아니기 때문입니다.

- **사용자 개입 경로** — 공공 데이터가 부정확할 수 있으므로, 사용자가 소화 체감을 직접
  변경하면 그 선택이 실측 지방량을 대체합니다. 더 무거운 쪽으로 바꾼 사용자의 판단을
  시스템이 무시하는 것은 안전 측면에서 잘못된 방향이기 때문입니다.

**"사용자는 자기가 먹은 음식의 지방량을 모른다"**

타이머는 지방량으로 계산하지만 사용자에게 "지방 몇 g 드셨나요?"라고 물을 수는 없습니다.
그래서 즐겨찾기 등록 시에는 **소화 체감을 세 단계**로만 고르게 하고, 계산 시점에
그램수로 환산합니다.

| 사용자 선택 | 환산값 | 결과 구간 |
|---|---|---|
| 가벼움 | 5g | 2시간 |
| 보통 | 15g | 3시간 |
| 무거움 | 30g | 4시간 |

환산값은 각 구간의 **안쪽에 배치**해, 사용자의 체감이 세 단계 수준에서만 맞으면 결과가
흔들리지 않도록 했습니다.

값의 우선순위는 다음과 같습니다.

```
1순위  AI 자동매칭으로 얻은 식약처 DB의 실측 지방량
2순위  사용자가 고른 소화 체감 → 환산값
```

기본적으로는 실측값을 사용하고, 실측값을 얻지 못했을 때 체감 환산값으로 대체합니다.
다만 사용자가 소화 체감을 **명시적으로 변경한 경우**에는 그 선택이 실측값을 대체합니다.

### 2. AI 음식 자동매칭

식약처 식품영양성분DB는 **100g 기준** 값을 제공하지만 사용자는 "1인분"을 먹습니다.
이 간극을 메우기 위해 Claude API를 두 지점에서만 제한적으로 사용합니다.

```
검색어 입력
   ↓
식약처 API 조회 (관련도순 상위 15개)
   ↓
이름 완전일치 항목 추출
   ↓
   ├─ 완전일치 1개 이상 ─→ 칼로리 중앙값에 가장 가까운 항목 선택   [순수 코드]
   │                        (동률이면 높은 쪽 — 과소평가 방지)
   │
   └─ 완전일치 0개 ──────→ 상위 10개 중 Claude가 후보 선택         [AI ①]
                             실패 시 관련도순 1위로 폴백
   ↓
1인분 그램수 추정 — Claude 3회 병렬 호출 → 중앙값                  [AI ②]
   실패 시 100g 기준으로 폴백 + 사용자에게 배지로 고지
   ↓
그램수 ÷ 100 × (100g당 칼로리·지방) = 최종값                        [순수 코드]
```

**AI는 새로운 영양성분 값을 생성하지 않습니다.** 완전일치 필터링, 중앙값 계산, 최종
환산은 전부 코드가 담당합니다. AI 호출이 실패해도 예외를 던지지 않고 폴백으로 이어져
**검색 자체는 절대 중단되지 않습니다.**

그램수 추정에 3회 병렬 호출 후 중앙값을 쓰는 것은 **자기일관성(self-consistency)**
기법으로, 단일 호출의 편차를 줄이기 위한 것입니다.

완전일치 후보 중 가공식품 비율이 **80% 이상**인 표준화 제품(라면, 과자 등)은 실제
제품의 1회 제공량을 웹 검색으로 확인하는 별도 경로를 탑니다.

## 실행 방법

### 백엔드

```bash
cd backend
cp src/main/resources/application-secret.properties.example \
   src/main/resources/application-secret.properties
# 위 파일에 실제 키 값 입력
./mvnw spring-boot:run
```

**Java 17** 필요. 로컬 MySQL에 `health_project` 데이터베이스가 준비되어 있어야 합니다.
별도 Spring 프로필 지정은 불필요합니다.

**필수 환경변수**

| 변수 | 용도 |
|---|---|
| `MYSQLHOST` / `MYSQLPORT` / `MYSQLUSER` / `MYSQLPASSWORD` / `MYSQLDATABASE` | DB 접속 정보 |
| `KAKAO_CLIENT_ID` / `KAKAO_CLIENT_SECRET` | 카카오 로그인 |
| `MFDS_SERVICE_KEY` | 식약처 오픈API |
| `ANTHROPIC_API_KEY` | Claude API |

배포 환경용 변수(`PORT`, `FRONTEND_URL`, `COOKIE_SECURE` 등)는
`application.properties`에 기본값과 함께 정의되어 있습니다.

### iOS

`ios/HealthProject/HealthProject.xcodeproj`를 Xcode로 열고 실행합니다.
서버 주소는 `APIConfig.swift`의 `baseURL` 상수에서 변경할 수 있으며,
기본값은 Railway 프로덕션 서버를 가리킵니다.

> **민감정보 안내**
> 카카오 client secret, 식약처 서비스키, Anthropic API 키는 제출본에서 제외했으며
> `application-secret.properties.example`에 형식만 남겨두었습니다.
> 운영 환경(Railway)에서는 환경변수로 주입합니다.

## 계산 공식 및 출처

### BMR / 목표 칼로리 — `BMRCalculator.swift`

**Mifflin-St Jeor Equation (1990)**

```
남성: BMR = 10 × 체중(kg) + 6.25 × 키(cm) - 5 × 나이 + 5
여성: BMR = 10 × 체중(kg) + 6.25 × 키(cm) - 5 × 나이 - 161
```

- 유지 칼로리(TDEE) = BMR × 활동계수
  (거의 안 움직임 1.2 / 가벼운 활동 1.375 / 보통 활동 1.55 / 활발한 활동 1.725)
- 증량 목표 = TDEE + 400 kcal (일반적으로 권장되는 300~500 kcal 범위 내)

### 러닝 소모 칼로리 — `RunAPIService.swift`

```
소모 칼로리 = MET × 체중(kg) × 시간(h)
```

속도 구간별 MET 값은 **2024 Adult Compendium of Physical Activities**의 달리기
항목을 참고했으며, 각 구간의 **하한 속도에 해당하는 값**을 사용했습니다.
(예: 7.0~8.0 mph 구간 → 7 mph = 11.0)
가장 느린 구간만 하한이 0이라 예외로, 원문의 최저 달리기 항목인 4 mph 값을 사용했습니다.

| 속도 (km/h) | MET | | 속도 (km/h) | MET |
|---|---|---|---|---|
| < 8.05 | 6.5 | | < 12.87 | 11.0 |
| < 9.66 | 8.5 | | < 14.48 | 12.0 |
| < 10.78 | 9.3 | | < 16.09 | 13.0 |
| < 11.27 | 10.5 | | ≥ 16.09 | 14.8 |

체중은 사용자가 입력한 값을 사용하며, 입력되지 않은 경우 부정확한 값이 기록에 남지
않도록 **저장을 차단하고 입력을 안내**합니다.

## 소화 타이머의 근거

### 왜 지방인가

**① 위는 부피가 아니라 열량을 기준으로 비웁니다.**

초기 30분 이후 십이지장으로의 에너지 전달 속도는 평균 2.5 kcal/min으로 수렴합니다
(Hunt et al., 1985). 지방은 1g당 9kcal로 탄수화물·단백질(4kcal)의 두 배 이상이므로,
**같은 1g을 더 먹었을 때 위 체류 시간을 가장 많이 늘리는 영양소**입니다.

**② 지방은 증상을 느끼는 민감도까지 올립니다.**

열량 밀도는 식도 산 노출의 정도를, 식이의 지방 비율은 역류 증상 빈도를 각각 독립적으로
결정합니다 (Fox et al., 2007). 십이지장에 지방이 도달하면 속쓰림 인지가 강화되는 기전도
확인되었습니다 (Meyer et al., 2001).

즉 지방은 **객관적 지표와 주관적 지표를 동시에 건드리는 유일한 영양소**이며, 그래서
부피나 총 칼로리가 아닌 지방을 단일 지표로 선택했습니다.

### 왜 10g과 25g인가

논문에 특정 그램 수 임계값은 존재하지 않습니다. 대신 **"평범한 한 끼가 몇 g인가"**를
서로 독립적인 세 기준으로 확인해, 그 범위의 경계로 설정했습니다.

| 기준 | 한 끼 지방 "보통" 범위 |
|---|---|
| 2025 한국인 영양소 섭취기준 (지방 에너지 15~30%) | 11 ~ 22g |
| 국민건강영양조사 실제 섭취 (1일 46g ÷ 3끼) | 약 15g |
| 위 배출 연구가 "저지방식"으로 정의한 값 | 9.2g |

**10g**은 세 기준 모두에서 보통보다 가벼운 쪽, **25g**은 모두에서 보통을 넘어선 쪽입니다.

## 알려진 한계와 대응

### 공공 데이터의 커버리지·품질 편차

식약처 식품영양성분DB를 직접 호출해 검증한 결과, 두 유형의 한계를 확인했습니다.

| 유형 | 사례 | 내용 |
|---|---|---|
| 항목 부족 | 곱창 | 전체 594건 중 이름 완전일치가 1건뿐이라 대안 없이 그 값을 사용 |
| 조리 상태 혼재 | 쌀국수 | 건면·조리식·즉석제품이 섞여 중앙값이 대표성을 잃음 |

쌀국수의 경우 건면 기준 값이 선택되어 지방이 실제보다 낮게 산출되며, 이는 **대기 시간이
실제보다 짧게 안내되는 방향**이라 건강 기능에서는 더 주의가 필요한 오차입니다.

**현재 대응**

- 사용자가 소화 체감을 직접 변경해 실측값을 덮어쓸 수 있는 경로 제공
- 구체적인 검색어일수록 완성된 요리 항목이 매칭되도록 안내

**향후 개선 과제**

- 조리 상태(생것/건조/조리완료) 구분 분류 도입
- 다중 데이터 소스 교차 검증
- 이상값 탐지 — 칼로리는 높은데 지방이 비정상적으로 낮은 패턴 경고

> 영양성분 값 자체를 AI 추정으로 대체하는 방향은 **채택하지 않았습니다.**
> 출처를 제시할 수 없는 값은 건강 관련 기능에서 근거가 될 수 없으며,
> "AI는 값을 생성하지 않는다"는 설계 원칙과도 충돌하기 때문입니다.

### 인증 방식

현재 세션 기반 인증을 사용하며, 서버 재시작 시 세션이 초기화됩니다.
토큰 기반 인증으로의 전환은 향후 과제로 관리하고 있습니다.
